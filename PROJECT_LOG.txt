■ .rk クラス衝突 → rank:item:null が783件（解析汚染）
  原因: 人気ランキングのクリック判定が t.closest('.rk') で
        クラス名 .rk を無条件に拾う。
        しかし .rk はサイト内で8箇所も別用途で使用されている
        （プレイヤーウォッチのランク表示 / 通信簿 / 代行 /
          リーダーボード / nbar など）
        さらにホームのマップウィジェットで .rk を追加してしまった
  影響: 画面は壊れない。マップのタップも動く。
        ただし解析に783件の幽霊クリックが混入し数字が嘘になる
  修正（find→replace 2種・4箇所）:
    (1) t.closest('.rk')            → t.closest('.rk[data-kind]')
    (2) hmCell('ランク',rk,'rk')     → hmCell('ランク',rk,'hm-rk')
        .hm-cell.rk{...}            → .hm-cell.hm-rk{...}
        .hm-cell.rk .hm-lab{...}    → .hm-cell.hm-rk .hm-lab{...}

【5】調査結果（確定事項）
================================================================
■ レジェンドのピック率データ
  → API経由では取得不可。
     api.mozambiquehe.re の提供は map / stats / servers / leaderboard /
     match history / news / store のみ。ピック率エンドポイントは無い。
     apexlegendsstatus.com/game-stats/legends-pick-rates と /meta に
     ページとしては存在するが、取るならスクレイピング（ToS/破損リスク）。
  → 現実解: パッチ単位でしか動かないので手動テーブルを年数回更新。
            「2026年7月時点」と明記すれば誠実。
  → ユーザー判断: API経由が無いならオミット（保留）

■ 大会 / イベントカレンダー
  → Liquipedia に ALGS 日程あり（APAC North の JST 表記まである）。
     ただしブラウザから直接不可（User-Agent必須・CORS・レート制限・
     CC-BY-SA表記義務）→ Cloudflare Worker 経由が必要。
     第三者のLiquipedia APIサービスは Valorant/CS/LoL/Dota2 のみでApex非対応。
  → 現実解: ALGSは年間日程がほぼ確定 → 手動テーブルで十分。
  → ユーザー判断: 自動が無理ならオミット（保留）

■ Firebase Authentication（2026-07時点）
  ・無料枠 = 月間アクティブ5万人まで完全無料
    （このサイトはWAU 507 → 余裕）
  ・対応: Email / Google / Facebook / Twitter(X) / GitHub / Apple /
          Microsoft / Yahoo
  ・SMS認証のみ有料（使わない）

■ X（Twitter）ログイン
  ・Firebase の Twitter プロバイダは X Developer の
    API Key / Secret（OAuth 1.0a）が必要
  ・X API 2026の無料枠 = 投稿50/日・読取1万/月
    Basic $200/月 / Pro $5,000/月
  ・OAuth 1.0a は X 側で「レガシー」扱い（推奨は OAuth 2.0 PKCE）
  → 無料枠で 3-legged ログインが通るか未確証。
  → 結論: まず Google ログインで作る（確実に無料・確実に動く）。
          X は後から数クリックで追加可能。要検証。

■ GAS ではリアルタイムチャットは不可（確定）
  ・WebSocket / SSE なし → ポーリングしかない
  ・同時実行30の上限。マップ・戦績・アンケート・代行が同じGASを共有
    → チャットのポーリングでサイト全体が詰まる
  ・応答が数百ms〜数秒 → チャットとして成立しない
  → 結論: Firebase Realtime Database を使う（WebSocket・無料枠で足りる）

■ localStorage ゲートは機能しない（重要・確定）
  ユーザー案「localStorageに保存できない環境ではチャット不可にすれば
  凍結された奴は二度と戻れない」は成立しない。理由:
  ・X内蔵ブラウザもシークレットモードも localStorage は
    「その場では普通に書ける・読める」。消えるのはセッション終了後。
    → 「書けるか？」のテストは全部パスする＝誰も弾けない
  ・仮に弾けても「サイトデータを消去」は10秒 → 新しい身元になる
  → 凍結を本物にする唯一の方法はアカウント（= Firebase Auth）
  → 副次効果: 以前の「人単位で数えたい」問題も同時に解決する

【6】チャット機能（仕様確定）

■ 確定した基盤【2026-07-16 変更：Firebase → GAS のみに方針転換】
  運営者の要望「GASだけで完結させたい」により Firebase を不採用。

  ・ログイン : Google Identity Services (GIS) を単体で使う
               ★重要な発見: GISはFirebaseなしで単体で動く。無料。
                 → 本物のGoogleアカウントIDが取れる＝【凍結が効く】
                 → 「凍結を本物にするにはFirebaseが要る」という
                   アシスタントの以前の主張は誤り。撤回済み。
               流れ: サイト→GIS→IDトークン(JWT)→GASへ送信→GASが検証
  ・保存     : スプレッドシート（90日ログ）
  ・高速読み : CacheService（直近100件をキャッシュ。
               毎回シートを読むと遅すぎる）
  ・受信     : 3秒ポーリング ?since=<ts> で差分のみ
  ・送信     : POST → LockService で排他 → シート追記 + キャッシュ更新
  ・判定処理 : 全部GAS側（レート制限3秒 / 140字 / NGワード /
               連絡先フィルタ / URL禁止 / 凍結チェック /
               通報3人で自動非表示 / 24h表示 / 90日ログ）
               ★Firebaseのルールでは書けなかった「件数を数える」処理が
                 GASなら普通に書ける＝ここはGASの方が楽

  ■ 飲んだトレードオフ（運営者が承認済み）
    ・リアルタイムではない。送信→相手に届くまで【1〜5秒】
      （3秒待ち + GAS応答0.2〜2秒）。Firebaseなら0.1〜0.3秒だった。
      → 運営者回答「OK」
    ・「もっさりしたチャット」になる。ポンポン会話する用途には向かない。

  ■ 必須条件（運営者が承認済み）
    ★【チャット専用のGoogleアカウントを新規作成する】
      理由: GASのクォータは【スクリプト単位ではなくGoogleアカウント単位】。
            同時実行は30まで。
            今の1アカウントがマップ・プレデター・サーバー・解析・
            アンケート・代行を全部さばいている。
            そこにチャットのポーリングを乗せると、チャットが混んだ瞬間に
            【マップが落ちる・戦績が落ちる・解析が止まる】。
            チャットは「あれば嬉しい機能」だが、
            プレイヤーウォッチ(21,945)とマップ(10,043)は生命線。
            それを人質に取る設計は不可。
      → 専用アカウントに隔離すればチャットが詰んでも本体は無傷。
      → 運営者回答「OK」

  ■ 未確定（実測するしかない）
    Webアプリの【日次実行時間の上限】が公式ドキュメントに明示されていない。
    ・「トリガーの合計実行時間 = 90分/日（消費者アカウント）」は明記あり
    ・Webアプリの実行は「トリガーより上限が高い」とだけ書かれ数字が無い
    ・同時実行30 は確認済み（アカウント単位・全スクリプト共有）

【6-3】運営者の仕様に対する修正（3件・全て運営者が承認済み）
================================================================
■ 修正1【承認済み】凍結ユーザー一覧の「公開」は作らない
  → 運営者回答:「管理画面の中（あなただけが見る）だけです。公開しない。」
  運営者案: 凍結ユーザーを一覧公開。X等の情報も記載しリンクを貼る。
            「気を付けようとなるので他の被害を減らせる」
  → 管理画面の中（運営者だけが見る）なら作る。むしろ必要。
  → 公開は不可。理由:
     ・凍結の判断は運営者1人。裁判でも審査でもない。誤爆は必ず起きる
     ・「凍結した」は事実でも、公表して本人のXへ誘導すれば名誉毀損になり得る。
       真実性の抗弁で求められるのは「凍結した事実」ではなく
       「その人が実際に悪事を働いた事実の立証」
     ・運営者が一覧の"発信者"になる。プロバイダ責任制限法の免責は
       媒介者のためのもので、ここでは効かない
     ・実際に起きるのは「気を付けよう」ではなくXへの凸。
       運営者が凸の起点になる
     ・誤爆1件で終わる

■ 修正2【承認済み】「1日100通報で自動凍結」は一生発火しない
  → 運営者回答:「いいよ。」（自動非表示3人 / 凍結は人間が判断 で確定）
  WAU 507 / 1日の訪問210-320 / チャット同時接続はせいぜい数十人
  → 100通報＝週間ユーザーの20%が1人を通報する必要。到達不可能＝死んだコード
  確定する代替設計:
    ・自動凍結はしない（凍結は人の人生に触る操作。人間が最終判断）
    ・自動"非表示"はする:
        異なる3人から1時間以内に通報 → 全員から自動で見えなくする
        + ダッシュボードに上げる
    ・「異なる3人」が肝。同一人物の連打は数えない（虚偽通報対策）
    ・凍結は必ず運営者の手で
  → 実際に発火し、誤爆しても非表示なので取り返しがつく

■ 修正3【承認済み】「24時間で流れる」と「監視」が矛盾している
  → 運営者回答:「OKです。」（表示24h / ログ90日保持 で確定）
  24時間で消えたら、後から通報ユーザーの全発言を見られない
  → 表示は24時間 / ログは別枠で90日保持（監査ログ）
     開示請求が来た時にも必要

【8-2】GAS制限時の仕様（確定 2026-07-16）
================================================================
考え方は2段構え。①そもそも当たらない設計 ②当たった時に何が起きるか。
①の方が圧倒的に大事。

■ ① 予防：限界に当たらない設計
  ★最大の脅威は荒らしでも同時接続でもなく「ポケットの中のタブ」
    チャットを開いたまま8時間放置 × 3秒ポーリング = 1人で9,600リクエスト。
    これ1人でクォータが飛ぶ。

  対策:
   ・【無操作5分で停止】→「まだ見てる？」→タップで再開  ← 一番効く
   ・【タブが裏に回ったら停止】visibilitychange。モバイルでは必須
   ・【閉じたら停止】開いてる人だけが叩く
   ・【静かなら間隔を伸ばす】誰も喋ってない → 3秒→10秒
   ・【差分だけ返す】?since=<ts>。新着ゼロなら {n:0} の超軽量応答
   ・【CacheServiceで応答】毎回スプレッドシートを読まない

■ ② サーバー主導のポーリング間隔（肝）
  GASが毎レスポンスに nextPoll を入れて返し、クライアントは黙って従う。
    { "msgs":[...], "nextPoll":3000 }   ← 平常
    { "msgs":[],    "nextPoll":15000 }  ← 混雑
  ★これにより、運営はGASの1行を変えるだけで全員の負荷を下げられる。
    index.html の再デプロイ不要＝詰まった時に打てる手が手元に残る。

■ ③ 予算の自己管理（Googleに殺される前に自分で落とす）
  GASが自分の1日のリクエスト数を数える。
    〜70%    : 通常（3秒）
    70〜90%  : nextPoll=10秒 +「混み合っています」
    90〜100% : nextPoll=30秒。送信は死守
    100%     : 受信停止。【送信だけは最後まで通す】
  ★受信を削って送信を守る。理由は下記Lv2。

■ ④ 4段階の劣化
  Lv0 正常
      3秒ポーリング。何も表示しない。

  Lv1 混雑（応答が遅い/たまに失敗）
      検知: 応答2秒超が続く / 単発の失敗
      動作: nextPollに従って自動で間隔を伸ばす（3→6→12→30秒）
      表示: ヘッダーに小さく「⏳ 混み合っています」
      チャットは使えたまま。

  Lv2 送信失敗
      検知: POSTがエラー
      動作: メッセージをローカル保持 + 自動リトライ3回（指数バックオフ）
      表示: 吹き出し「送信中…」→ 失敗なら「⚠️ 送信できませんでした ［再送］」
      ★絶対にメッセージを消さない。
        ユーザーが打った文字が消えるのが一番腹立つ。
        失敗しても吹き出しは残し、再送ボタンを出す。

  Lv3 GASが死んだ（クォータ超過）
      検知: 【JSONじゃない応答が返る】or 5回連続失敗
      動作: ポーリングを完全停止（叩き続けても無駄。回復を妨げる）
            + 入力欄を無効化
      表示: 「チャットが一時的に利用できません。
             今日の上限に達した可能性があります。
             しばらくしてから開き直してください」
      復帰: 60秒に1回だけヘルスチェック。生き返ったら自動復帰。

  Lv4 緊急停止（運営が手動）
      GASの chatEnabled = false
      全クライアントが次のポーリングで受け取って即クローズ。
      寝てる間に荒れた時の最後の手段。

■ ⑤ 検知の要：「JSONじゃない応答」★技術的なポイント
  GASはクォータを超えるとJSONではなく【HTMLのエラーページ】を返す。
  スクリプト自体が起動しないので、GAS側でエラーを捕まえて
  {ok:false} を返すこともできない。
  → クライアント側で「返ってきたものがJSONとしてパースできるか」を見て、
    駄目ならGASが死んだと判定する。
  → JSON.parse() を必ず try/catch で囲む。
    忘れると画面が真っ白になって原因不明のバグになる。

■ ⑥ 正直に：この設計でも防げないこと
  ・バズった瞬間は防げない。1日15,222訪問の日にチャットが開いていたら
    たぶん昼で予算が尽きる → Lv3。
    ただしチャットだけが死んでサイトは無傷（専用アカウントなので）。
    それが受け入れ可能な最悪ケース。
  ・日次上限の実数が不明なので、最初の予算は当てずっぽう。
    1〜2週間動かして実測してから調整する。

【9】自動非表示の仕組み（GAS版・確定）
================================================================
■ Firebase時代の問題は消滅した
  Firebaseのセキュリティルールには「件数を数える」機能が無く、
  「異なる3人が通報したら非表示」が書けなかった。
  → GASなら普通に書ける。ここはGASの方が圧倒的に楽。

■ 仕様
  ・ユーザーが通報 → GASが /reports に記録（1人1メッセージ1回だけ）
  ・GASが【送信/ポーリングのついでに】その場で集計する
    （別途トリガーを立てる必要すらない）
  ・1時間以内に【異なる3人】から通報 → hidden=true
    ★「異なる3人」が肝。同一人物の連打は数えない（虚偽通報対策）
  ・同時に modQueue に積んでダッシュボードへ
  ・【自動凍結はしない】凍結は人の人生に触る操作。運営が手動で判断。

■ GASなので改ざん不可
  判定は全部サーバー側。クライアントは通報を投げるだけ。
  devtoolsから偽の判定を送っても無視される。
  ★Firebase版で懸念していた「クライアント判定はゲームされる」問題は
    GASでは最初から存在しない。

■ hidden の扱い
  hidden=true のメッセージはGASが返さない（レスポンスに含めない）。
  ★Firebase版では「RESTを直接叩けば読めてしまう」という限界があったが、
    GASはサーバー側でフィルタするので【本当に見えなくなる】。
    ここもGASの方が強い。

【ALGS大会解説LP】発熱対策＋横揺れ再修正（2026-07-20）

ファイル: algs-guide-dark.html (69KB) ※見た目は維持

■ 発熱の原因(特定)

  (2) 巨大blur(90px)+ blur/box-shadow/drop-shadowの無限アニメ(GPU最苦手)
  (3) 画面外の要素までアニメが動作し続けていた
  (4) DPR=2でRetina4倍描画
  (5) createLinearGradientを毎フレーム生成

■ 実装した対策(見た目を保つ裏側最適化を全部)
  描画: DPR=1固定 / 30fps上限 / スクロール停止で自動休止(idle 1.2s) /
        タブ非表示でcancelAnimationFrame完全停止 /
        粒をオフスクリーンcanvasにsprite化しdrawImage(arc/gradient廃止) /
        グラデ毎フレーム生成を全廃 / sqrt廃止(二乗比較) /
        端末性能(hardwareConcurrency)・モバイル・saveDataで粒数自動調整 /
        アクセント色更新を4フレームに1回
  GPU: グローblur 90→38px / floor-reflect blur削除 /
        backdrop-filter削除(モバイル激重)→半透明黒 /
        trophyshineのdrop-shadowアニメ廃止→transformのみ+静的shadow /
        goldframe/softblink/edgeglowのbox-shadowアニメ→opacityに置換 /
        progress二重shadow→1つ
  アニメ制御: 画面外の常時アニメをIntersectionObserverでpaused(37) /
        無限アニメの周期を延長(更新頻度↓) /
        content-visibility:auto で画面外セクションの描画スキップ /
        FPS実測(2秒)して24fps未満なら重い背景アニメを止めcanvas非表示(自動軽量化)

■ 横揺れ(左右に動く)再修正
  原因: sec-ghost(章番号の巨大78-88px文字)がright基準で右にはみ出していた
  対策: section .wrap に overflow:hidden、sec-ghost を right:0/78px/overflow:hidden /
        html・body・section すべて overflow-x:clip(hiddenより確実) /
        グローの横パララックス(x)も除去済み
  結果: 横方向にはみ出すtransformはゼロ(残るtranslateXは-50%中央/nav隠し101%のみ)
